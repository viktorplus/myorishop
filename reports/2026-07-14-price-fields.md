# Отчёт: ценовые поля товара и каталога — где какая цена используется

Дата: 2026-07-14

## Задача

Разобраться в путанице между полями «Закупочная цена», «Цена продажи»,
«Минимальная цена продажи», «Цена по каталогу» (на карточке товара) и
«Цена по каталогу» / «Цена консультанта» (в справочнике каталогов),
и точно определить, какая цена подставляется при продаже.

## Где какая цена хранится

| Русское название | Поле в коде | Таблица | Кто пишет |
|---|---|---|---|
| Закупочная цена | `Product.cost_cents` | `products` | форма товара (создание/редактирование) |
| Цена продажи | `Product.sale_cents` | `products` | форма товара |
| Минимальная цена продажи | `Product.min_sale_cents` | `products` | форма товара |
| Цена по каталогу (на карточке товара) | `Product.catalog_cents` | `products` | форма товара, один раз при автозаполнении |
| Цена по каталогу (справочник каталогов) | `CatalogPrice.consumer_cents` (ПЦ) | `catalog_prices` | только импорт прайс-листа |
| Цена консультанта | `CatalogPrice.consultant_cents` (ОП/ДЦ) | `catalog_prices` | только импорт прайс-листа |
| Цена партии (внутреннее) | `Batch.price_cents` | `batches` | при создании прихода, копируется из поля «Цена продажи» в приходе |

`CatalogPrice` (каталог) и поля `Product` — это **разные, независимые**
значения, не связанные автосинхронизацией.

## Что подставляется при продаже — пошагово

1. Оператор вводит код товара → система показывает подсказку по цене
   **только из `Product.sale_cents`** («Цена продажи»). Ни закупочная, ни
   каталожная цена сюда не попадают.
   (`app/services/sales.py:281-303`, `lookup_prefill()`)
2. Дальше выбирается **партия**. Если у партии есть своя зафиксированная
   цена (`Batch.price_cents`, заданная при приходе) — в поле подставляется
   **она**, а не `Product.sale_cents` («Цена подставлена из партии — можно
   изменить»). (`app/routes/sales.py:152-154`)
3. Если у партии цены нет (старая партия) — подставляется
   `Product.sale_cents` («Цена подставлена из карточки товара — можно
   изменить»). (`app/routes/sales.py:156-157`)
4. Это **всегда только подсказка** — поле редактируемое, оператор может
   вписать любую цену вручную.
5. При сохранении продажи в базу пишется именно то, что оператор ввёл в
   поле — это обязательное поле (`app/services/sales.py:127-143`), без
   него продажа не пройдёт.
6. `Product.min_sale_cents` — ограничитель: если введённая цена ниже
   минимума, продажа блокируется с предупреждением
   (`app/services/sales.py:206-234`). **Но** это предупреждение можно
   обойти той же кнопкой «подтвердить всё равно», что и для превышения
   остатка (`confirm=1`, `sales.py:181`) — то есть минимальная цена не
   жёсткий запрет в БД, а совет с возможностью обхода.
7. **«Цена консультанта» и «Цена по каталогу» из справочника каталогов
   (`CatalogPrice`) в продаже вообще не участвуют.** Они используются
   только:
   - при автозаполнении карточки товара (код → подставляет
     `cost_cents`/`catalog_cents` один раз, если поля пустые) —
     `app/routes/products.py:143-152`, `app/services/pricing.py:14-32`;
   - при подсказках в форме прихода — `app/services/receipts.py:283-296`;
   - на странице просмотра каталога — `app/templates/pages/catalog_detail.html:20-21`.

## Синхронизация с импортом прайс-листа

`Product.sale_cents`, `Product.cost_cents`, `Product.catalog_cents`
**независимы** от `CatalogPrice` и не пересчитываются при повторном
импорте прайс-листа. `scripts/import_master_pricelist.py` трогает только
таблицы `Dictionary`/`CatalogPrice`, никогда не изменяя `Product`
(`import_master_pricelist.py:14`). `app/services/receipts.py:266-268`
явно фиксирует: «`sale` is ALWAYS None on this branch — этот магазин
никогда не берёт свою цену продажи из каталожных данных Oriflame».

Поля товара заполняются из `CatalogPrice` только один раз — при
создании/редактировании товара, и только если поле было пустым
(`app/routes/products.py:144-145`).

## В чём путаница (найдено в коде)

- **`Product.catalog_cents` vs `CatalogPrice.consumer_cents`** — по сути
  одно и то же («Цена по каталогу»), но хранятся отдельно.
  `Product.catalog_cents` заполняется один раз при создании/редактировании
  товара и потом не обновляется, даже если переимпортировать новый
  прайс-лист с другими ценами. На странице редактирования товара это
  явно показано двумя строками рядом («сохранённая» и «последняя из
  каталога», `product_form.html:104-111`) — именно потому что они могут
  разойтись.
- **`Product.cost_cents` (Закупочная) vs `CatalogPrice.consultant_cents`
  (Цена консультанта)** — та же история: заполняется один раз при
  автоподстановке кода, дальше живёт своей жизнью, не синхронизируется с
  новым импортом каталога.
- **«Цена продажи» vs «Цена по каталогу»** — по смыслу разные вещи (своя
  цена продажи vs розничная цена Oriflame по каталогу), но легко перепутать
  на глаз. В продаже участвует только `sale_cents`.
- Название **«Цена консультанта»** на странице каталога
  (`catalog_detail.html:21`) и просто **«консультант»** на карточке товара
  (`product_form.html:110`) — это одно и то же поле
  (`CatalogPrice.consultant_cents`), но подписано по-разному в двух местах
  интерфейса.
- **`min_sale_cents` обходится через `confirm=1`** — тот же механизм
  «подтвердить оверселл», что и для остатка на складе, снимает и проверку
  минимальной цены за один флаг (`sales.py:181`). UI подаёт это как
  жёсткий барьер, а по факту это обходимое предупреждение — стоит
  подтвердить, что так и задумано.

## Возможные следующие шаги (не сделано, требуют решения пользователя)

- Унифицировать подписи «Цена консультанта» / «консультант» в UI.
- Добавить на карточку товара кнопку «обновить из последнего прайс-листа»,
  чтобы `catalog_cents`/`cost_cents` не расходились с `CatalogPrice`
  молча.
- Решить, должна ли минимальная цена быть жёстким ограничением (без
  возможности обхода) или это осознанный дизайн.
