# Quick Task 260810-2g3 — Currency correctness, part 2

Part 1 (`cdcec66`) added `Warehouse.currency` and stopped there: reports, the
dashboard and finance still summed across currencies, a sale basket could mix
warehouses of different currencies, and a transfer carried the source batch's
price into a warehouse where that number means nothing. This task closes all of
it.

No FX rate, no conversion, no base-currency roll-up was added — anywhere. A
currency filter always resolves to exactly one currency; a cross-currency total
is not computable in the app.

## Locked decisions as implemented

1. **Cash carries a currency.** Migration 0024 backfills every existing row to
   RUB `NOT NULL`, so no cash row is ever currency-less. Auto sale-credit /
   return-debit inherit the currency of the sold batch's warehouse; the manual
   form has a currency select. `compute_balance`, `cash_history_view`,
   `cash_flow_report`, `cash_expense_total` each take a currency and never SUM
   across two.
2. **`Batch.cost_cents`** holds the cost in ITS warehouse's currency. The
   receipt form's existing «Закупочная цена» now stamps it (no new UI). A sale
   freezes `unit_cost_cents` from the batch, falling back to
   `Product.cost_cents` when NULL — so every pre-existing row behaves exactly
   as before.
3. **Single-currency reports.** `/reports/sales`, the `/finance` stock
   valuation and the dashboard each filter to one currency, RUB by default.
   `stock_valuation` was rewritten onto a `Batch`+`Warehouse` join — the old
   `Product.quantity * Product.cost_cents` form had no warehouse dimension at
   all and could not be scoped.
4. **No mixed-currency basket.** `register_sale` rejects a basket spanning
   warehouses of different currencies with a Russian error, before any write.
5. **Legacy rows are RUB** (operator decision). `Operation.batch_id` is
   nullable, so pre-Phase-9 rows cannot resolve a warehouse. They bucket as
   `DEFAULT_CURRENCY` via `operation_currency_clause()` — one shared helper
   using an **outer** join + `COALESCE`, never an inner join, which would have
   silently dropped those rows from the RUB report instead of counting them.

An extra migration (0026) was needed and not foreseen in the plan: the
append-only trigger on `cash_movements` enumerates columns, so the new
`currency` column had to be added to its guard or the trigger would not have
protected it.
