<objective>
Restore the product type on the dictionary rows that kept only a shade name, by inheriting
the type from the series header row of the Oriflame price lists — for the ~605 codes where
the справочник currently holds nothing but the colour.

Purpose: «Фарфоровый» is not a product. Such a row cannot be found by name, and in the
«Офис» inventory it prints as a colour with no object (5 of the 605 are in that inventory:
32287, 33155, 33157, 33158, 33159). The price list itself carries the answer — the type is
written once, in the first row of the series, and every following row starts with a dash.

Output: two extended importers (no new script), one shared predicate in
`app/services/rubrics.py`, ~605 appended entries in `app/services/rubric_overrides.json`,
the locally-applied restoration, a re-issued `catalogs/products.json`, and a documented
command the orchestrator can run on s1 that is structurally incapable of touching a
hand-written name.
</objective>

**The key design decision, already made — how an EXISTING row's name gets updated.**
`--only-missing` only inserts, and a full replace on s1 would erase the 4 hand-written
names. The answer is neither an allow-list nor a blacklist but a **predicate**:
`is_shade_tail(current, restored)` is true only when the current name is exactly the tail of
the restored one after a « - » separator (case-folded, and strictly shorter). A hand-written
full name («Женская туалетная вода Sunkiss Garden объем 50 мл») can never be the shade tail
of anything, so it cannot be selected — safety comes from the data, not from a list somebody
has to maintain. The same predicate runs at generation time (which codes get an override)
and again row by row at apply time (which rows get rewritten), so the s1 command is identical
to the local one, needs no extra file, and is idempotent: after the first run nothing matches
any more. Both write modes are **dry-run by default** and need `--apply`, mirroring
`scripts/import_inventory_receipt.py`.

**Where the code goes.** No new script. The price-list archive is already owned by
`scripts/import_prices.py` (`parse_catalog`, `_find_header`, `_is_code`, `_norm`, `_cell`) —
the restoration reuses those primitives rather than growing a second header finder, so the
generator lives there. The DB-side update belongs to `scripts/import_catalogs.py`, which
already owns `dictionary` writes. The shared predicate goes to `app/services/rubrics.py`,
which both scripts already import and whose docstring already describes exactly this class of
«name is only a colour/shade» codes.

**Reading `.xls`.** Today `import_prices.py` reads only `*.xlsx` via openpyxl, so the 118
`.xls` files are invisible to it. The restoration needs both. `xlrd` (2.x, `.xls` only) is
NOT a project dependency and must NOT become one — it is used ad hoc through
`uv run --with xlrd …`. Consequences to respect:

- both `openpyxl` and `xlrd` are imported INSIDE the reading function (the image builds with
  `uv sync --frozen --no-dev`; the existing AST test pins this for openpyxl and must be
  extended to xlrd);
- xlrd returns numbers as floats, so `33155` arrives as `33155.0` and `_is_code` would reject
  it — integral floats must be normalised to `int` at the row-reading boundary, before any
  existing helper sees them;
- the price-import path keeps its `*.xlsx`-only glob; wiring `.xls` into `catalog_prices` is
  NOT part of this task.

**Style.** ruff, line-length 100, `select = E,F,I,UP,B`. Scripts do `sys.path.insert(...)`
before app imports with `# noqa: E402` — keep that shape. pytest has `pythonpath = ["."]`, so
`from scripts.import_prices import …` works with no `__init__.py`. Portable ORM only (s1 is
PostgreSQL): no `sqlalchemy.dialects`, no `INSERT OR`, no `on_conflict`, no `strftime`.

**Byte form of `rubric_overrides.json` (confirmed in 260902-1d1):** `indent=1`,
`ensure_ascii=False`, inner keys in `conf, name, rubric` order, **CRLF** line endings, ends
with `\r\n}` and **no trailing newline**, and the key order is insertion order (NOT sorted —
the 1d1 batch sits at the end, after larger keys). New entries are appended; not one existing
line may be rewritten.
