# Импорт описи склада «Офис» как прихода — правила, утверждённые оператором

Источник: `reports/оприходование-офис-2026-08-31.csv` (UTF-8 BOM, `;`, 414 строк
данных). Колонки: `Полка;Код;Наименование (из справочника);Кол-во;Срок годности;
Срок (как в записи);Комментарий;Файл-источник;Проверить`.

## Что это за операция

Опись — **список товара на добавление**, а НЕ инвентаризация. Всё, что уже
лежит на складе, остаётся; опись добавляется сверху. Пересечение с
существующими остатками — это доп. поступление, а не задвоение.

Оператор сформулировал так: «список товаров на добавление состоит из новых
товаров, те товары которые уже есть остаются, к ним дополнительно добавляются
новые».

## Правила

1. **Строки.** Берём только строки с непустым кодом. Строка с кодом `???`
   (индекс 312) пропускается — её нечего оприходовать. Итого 413 строк,
   332 уникальных кода, 2204 шт.

2. **Ключ партии — код + ГОД-МЕСЯЦ срока + признак состояния.**

   2.1. **Год-месяц, а не точная дата.** В базе сроки записаны числами 14 и 18
   (`2018-01-14`), а опись разворачивает `ММ/ГГ` в последний день месяца
   (`2018-01-31`). Это один и тот же лот. Сопоставление по дню плодило бы дубли
   партий одного месяца, поэтому день игнорируется. Пустой срок совпадает
   ТОЛЬКО с пустым.

   - есть партия того же товара в складе назначения с тем же годом-месяцем →
     **долив** (`batch_choice=<batch.id>`); срок этой партии приводится к виду
     описи (последний день месяца) — только у партий, которых касается импорт;
   - несколько партий одного месяца → берётся с самой ранней датой, сухой
     прогон печатает предупреждение (в текущих данных таких нет);
   - партии с таким месяцем нет → **новая партия** (`batch_choice="new"`);
   - товара в базе нет → карточка создаётся сервисом, партия новая. Несколько
     строк с разными месяцами дают несколько партий.

   2.2. **Признак состояния перебивает совпадение срока.** Партия может быть
   новой даже при совпавшем сроке — по иному критерию, записанному в примечании
   рядом с размещением (например, «упаковка повреждена», «пробник», «вскрыто»).
   Признак берётся ИЗ ВХОДЯЩЕЙ строки описи, а не из партии в базе:

   - колонка `Комментарий` разбирается на размещение (`полка NN` или
     `под зеркалом`) и остаток. Остаток и есть признак состояния;
   - остаток непустой → строка ВСЕГДА получает новую партию, долив запрещён,
     признак пишется в `comment` новой партии рядом с полкой;
   - две строки описи с одинаковыми кодом, месяцем и признаком идут в одну
     новую партию;
   - остаток пустой → обычное сопоставление по 2.1. Примечание существующей
     партии доливу НЕ мешает: на s1 три партии несут приписку «Срока на
     упаковке нет» — это пояснение к пустому сроку, а не признак состояния,
     и блокировать долив из-за неё нельзя.

   В текущей описи признаков состояния нет ни в одной из 414 строк: колонка
   `Комментарий` везде содержит только размещение. Правило закладывается на
   будущие описи, а сухой прогон печатает, сколько строк его задействовали.

3. **Полка.** Размещение из `Комментарий` → размещение партии.
   - новая партия: `location_raw` = `полка NN`;
   - долив: сервис `register_receipt` игнорирует примечание на пути долива,
     поэтому ПОСЛЕ успешного долива дописываем полку в `batch.comment`
     (партии не append-only, менять их можно), не дублируя уже присутствующую
     пометку. Сравнение — по частям `split("; ")`, не подстрокой: «полка 4»
     является подстрокой «полка 47».

4. **Цены.**
   - есть в `catalog_prices` → ДЦ в `cost_raw`, ПЦ в `sale_raw`;
   - нет → **пустая строка** (поле остаётся `NULL`). Не ноль. Оператор:
     «если нет оставим пустое поле, программа это позволяет, цена будет
     определена в момент продажи или добавлена в справочник позже».
   - Цены передаются ТОЛЬКО для кодов, которых ещё нет в `products`. Для уже
     существующих карточек передаём пустые строки, иначе `register_receipt`
     пишет `price_change` и перетирает цену карточки каталожной.

5. **Название.** Из колонки `Наименование (из справочника)`. Для существующей
   карточки сервис его игнорирует (PD-9) — это ожидаемо.

6. **Собственные коды оператора** `0001` «Барьер» и `0002` «Соковыжималка»
   (на листе записаны словом, артикула Oriflame нет) — импортируются как есть,
   в справочник НЕ добавляются.

7. **Склад назначения** — «Офис». На s1 это
   `88b67b10-df5d-43dd-9651-34877a3d957e`. Id НЕ хардкодить: искать активный
   склад по имени, регистр не важен; если не найден — падать с внятной ошибкой.

## Требования к скрипту

- Новый `scripts/import_inventory_receipt.py`; работает и на SQLite, и на
  PostgreSQL (диалект берётся из `app.config.settings`, как в
  `scripts/reset_business_data.py`).
- Пишет ТОЛЬКО через `app.services.receipts.register_receipt` — никаких прямых
  INSERT в `products` / `batches` / `operations`. Исключение: апдейт
  `batch.comment` по правилу 3.
- Режим по умолчанию — **сухой прогон**: печатает план (сколько новых карточек,
  новых партий, доливов, сколько строк без цены) и НИЧЕГО не пишет.
  Запись только по явному флагу `--apply`.
- `--warehouse <имя>` (по умолчанию «Офис»), `--file <путь>`.
- Идемпотентность не требуется и не изображается: повторный `--apply` добавит
  количество ещё раз. В сухом прогоне печатать предупреждение об этом.
- Любая ошибка валидации от `register_receipt` = стоп с указанием номера строки
  CSV и текста ошибки; уже записанные строки не откатываются (журнал
  append-only), поэтому печатать, на какой строке остановились.
- Тесты: путь «новый товар», «долив при совпавшем месяце», «долив при
  РАЗНОМ ДНЕ одного месяца — 2018-01-14 и 2018-01-31 сходятся в одну партию»,
  «новая партия при другом месяце», «пустой срок совпадает только с пустым»,
  «признак состояния в примечании даёт новую партию вопреки совпавшему сроку»,
  «две строки с одинаковым признаком идут в одну партию», «пустая цена остаётся
  NULL», «строка без кода пропущена», «полка дописана в comment при доливе»,
  «полка 4 не считается уже присутствующей в „полка 47“».
