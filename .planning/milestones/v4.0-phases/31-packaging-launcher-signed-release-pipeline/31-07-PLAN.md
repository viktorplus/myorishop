<objective>
Close GAP-3 (blocker): one failed update bricks the installation. Three defects compound —
the third was found by the plan-checker against the first draft of this plan.

(a) `launcher/swap.py:86-88` — `stop_app()` and BOTH `os.replace` calls sit OUTSIDE the `try:` that
opens at line 89. Once `app\` has been renamed to `app.prev\`, a missing or already-consumed
`staged\` raises `FileNotFoundError` with no rollback handler in scope.
(b) `launcher/__main__.py:92` — `marker.unlink()` runs only after `apply_update` returns normally, so
a raised exception leaves `data\pending.json` in place and `main()`'s 2-second loop (lines 107-109)
replays the now-unsatisfiable cycle.
(c) The ROLLBACK's own two `os.replace` calls (swap.py:97-98) are equally unguarded, and NOTHING
ever deletes or rotates `app.failed\` — the happy path only `rmtree`s `app_prev`. On Windows
`os.replace` cannot replace an existing DIRECTORY: measured on this machine,
`os.replace(<dir>, <existing dir>)` raises `PermissionError [WinError 5]` for a NON-EMPTY *and*
for an EMPTY destination. So on the SECOND failed update `os.replace(paths.app, paths.app_failed)`
raises inside the `except` block, the `app.prev -> app` restoration never runs, and the end state
is the same brick the UAT recorded. Fixing (a) and (b) alone would close GAP-3 for exactly one
failure.

Observed end state after a real two-tick UAT run: `app=False, app.prev=True, app.failed=True,
staged=False, marker=True`, `app\python.exe` missing — the application directory no longer exists and
the marker is still there, so the cycle repeats on every relaunch.

Purpose: PKG-04's whole promise is that a failed apply leaves the operator running on the previous
version. Today the FIRST failure rolls back correctly and the SECOND tick destroys the install. This
path is load-bearing for Phase 32 (in-app self-update), which drives exactly this state machine.
Output: a guarded `apply_update`, a marker that is always consumed, a watch loop that survives a bad
tick, and the two-tick regression the UAT asked for.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staged\ + pending.json → launcher | Untrusted marker/staged code the launcher acts on; Phase 32 gates staging behind signature + checksum verification |
| launcher → app\ / app.prev\ / app.failed\ | The four-directory rename swap; a partially-applied rename is the brick condition |
| launcher → data\ DB | The matched-pair rollback restores the pre-update DB; restoring it when nothing changed would itself be data loss |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-06 | DoS (data integrity) | half-applied update | mitigate | Both renames now sit inside the guarded region and the rollback undoes exactly the steps that ran; a missing `staged\` is refused BEFORE `stop_app` and before the first rename, so `app\` can never be renamed away with nothing to put back |
| T-31-06b | DoS (data integrity) | DB restore on a no-op failure | mitigate | `backup_restore` runs ONLY when the migration was actually attempted — a pre-swap failure leaves the operator's DB untouched instead of reverting it to an older backup and discarding intervening work |
| T-31-06c | DoS (data integrity) | stale directory blocking a rename | mitigate | Windows `os.replace` cannot replace an existing directory, empty or not (WinError 5 — measured). Every directory rename therefore clears its destination first: `app.prev\` before the forward swap, `app.failed\` before parking the bad code, and `app\` (rmtree fallback) before the restoration if parking failed. The `app.prev -> app` restoration sits outside the parking step's own try, so a second, third or Nth failed update rolls back exactly like the first |
| T-31-04 | Tampering / Elevation | replayed pending marker | mitigate | The marker is always consumed: deleted on success, moved to `pending.failed.json` on failure, and refused outright when its staged dir is gone — an unsatisfiable marker can no longer be replayed every 2 seconds |
| T-31-05 | Tampering | staged_dir / db_backup_path in marker | mitigate | `parse_pending`'s `..`/absolute/escape confinement (ASVS V12) is unchanged and still runs before the new existence check |
</threat_model>
