<objective>
Build PKG-04 — the stable launcher that makes a self-replace-while-running update possible on
Windows. A small stdlib-only process living OUTSIDE the swappable `app\` directory owns the app's
child PID directly, and on a hand-placed `pending.json` marker performs the transactional
stop → swap (directory renames) → `alembic upgrade head` → restart, with a matched-pair rollback
(previous code + pre-update DB) on any failure (ROADMAP Phase 31 criterion 4).

Purpose: The launcher is the only actor allowed to touch `app\` while the app is down; it lives
outside the swap target because Windows will not rename a directory containing a running process
(RESEARCH Pitfall 3, WinError 32). Phase 32's self-update drives this exact mechanism — Phase 31
proves it with a hand-placed staged dir + marker.
Output: `launcher/` package (pure swap state machine + Windows adapters + entry) turning
`tests/test_launcher.py` green.
</objective>

<artifacts_produced>
Artifacts this phase produces (introduced by THIS plan):

- Marker contract: `data\pending.json` = `{staged_dir, expected_version, db_backup_path}` (full IPC/controlled-shutdown contract DEFERRED to Phase 32; Phase 31 needs only the hand-placed-marker proof).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staged\ + pending.json → launcher | Untrusted marker/staged code the launcher acts on; Phase 32 gates staging behind signature/checksum verify — Phase 31 trusts a hand-placed dir ONLY in-test |
| launcher → app child | The launcher owns the child PID; stop is by owned handle, not by port |
| launcher → data\ DB | Rollback restores the pre-update DB; stale WAL sidecars must be deleted to avoid corruption |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-04 | Elevation / Tampering | launcher swaps staged code | mitigate | Launcher acts ONLY on a valid pending.json; refuses to swap otherwise. Content-trust (verify signature before staging) is the Phase 32 seam — Phase 31 must not create a path that swaps unverified code silently; per-user %LOCALAPPDATA% install limits blast radius (V10/V1) |
| T-31-05 | Tampering | staged_dir / db_backup_path in marker | mitigate | parse_pending resolves + confines both paths under install_root and rejects `..`/absolute escapes (V12) before any os.replace |
| T-31-06 | DoS (data integrity) | failed apply | mitigate | Matched-pair rollback: os.replace restores previous app\ AND backup_restore copies the pre-update VACUUM-INTO DB back, deleting -wal/-shm (RESEARCH Pitfall 4 / restore.bat parity) |
| T-31-03 | Tampering | pre-update DB anchor | mitigate | Rollback DB comes from the Plan-02 sibling backups\ (survives the swap); launcher never trusts a DB inside the swapped app\ |
</threat_model>
