# Phase 31 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.
> Phase 31 turns the dev checkout into a **shipped Windows artifact**: a per-user
> Inno Setup installer, an embeddable-Python onedir, a stable launcher that
> performs a stop → rename-swap → `alembic upgrade head` → restart cycle driven by
> an on-disk `pending.json` marker, and a two-stage signed-release pipeline whose
> secret key never enters CI. The attack surface is therefore **local filesystem +
> build/release supply chain**, not HTTP.
>
> Every `mitigate` row below was VERIFIED present in implemented code —
> documentation, plan text and SUMMARY claims were NOT accepted as evidence. Each
> row cites the exact line performing the control plus the test that proves it.
> The auditor independently re-ran
> `uv run pytest tests/test_packaging.py tests/test_launcher.py tests/test_release_verify.py -q`
> on 2026-09-03 at HEAD `dd1f5f2` → **48 passed, 0 skipped** (`minisign` is on the
> local PATH, so the sign→verify→tamper-fail round-trip genuinely ran rather than
> self-skipping; `dist/app/python.exe` and `dist/launcher/python.exe` exist, so the
> two real-runtime gates ran too).

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| python.org → build box | `fetch_embeddable` downloads the CPython embeddable zip over HTTPS and hash-checks it before it ever becomes `python.exe` | ~15 MB runtime, digest-pinned |
| PyPI → build box | `vendor_wheels` pip-installs the uv.lock-frozen requirement set into `Lib\site-packages` | Third-party wheels (see AR-31-SC-WHEELS) |
| GitHub Actions (Stage A) → draft release | CI builds + drafts; it holds **no** signing key and references **no** repo secret | Archive, installer, `SHA256SUMS`, `manifest.txt` — all UNSIGNED |
| offline machine (Stage B) → published release | A human signs `manifest.txt` with the offline Ed25519 secret key and publishes | `manifest.txt.minisig` only |
| release artifact → operator box | Installer writes `{localappdata}\MyOriShop`; no admin, no UAC, no service | Whole bundle |
| `data\pending.json` (attacker-writable file) → launcher swap | The ONLY input that can make the launcher rename directories and run `alembic` | Marker JSON: `staged_dir`, `expected_version`, `db_backup_path` |
| swappable `app\` ↔ operator state `data\` | Physical-sibling layout: the swap renames `app\` and structurally cannot reach `data\` | DB, backups, `secret_key`, `device_id`, `.env` |
| install root → launcher `sys.path` | The launcher `._pth` carries `..`, putting the install root on `sys.path` (accepted by design — AR-31-09) | Importable modules |

## Accepted Risks Log

| Risk ID | Threat Ref | Rationale | Accepted By | Date |

| AR-31-01 | T-31-01 | **The installer ships without a code-signing certificate; Windows SmartScreen will warn on first run.** Accepted at plan time (PKG-02 explicitly defers the certificate). Verified as a real posture, not an oversight: the generated `.iss` contains no signing directive whatsoever, and the RU one-time «Подробнее» → «Выполнить в любом случае» step is documented for the operator at `docs/RELEASE.md:133-147`. Compensating control verified in code: the bundle is the genuine python.org embeddable CPython (`build_release.py:82`) extracted verbatim, **not** a PyInstaller self-extracting stub — which is the packaging form that actually drives AV false positives. Residual: an operator trained to click through SmartScreen is an operator trained to click through SmartScreen; a spoofed installer would produce the same dialog. Bounded by distribution being a direct GitHub-release link plus the signed `manifest.txt` (T-31-03) that Phase 32's self-update verifies. **Revisit trigger:** any distribution channel wider than the single known operator, or the first Authenticode certificate purchase. | gsd-security-auditor | 2026-09-03 |
| AR-31-09 | T-31-09 | **The launcher's `python313._pth` puts the install root (`..`) on `sys.path`.** Accepted by design — it IS the mechanism by which `launcher\python.exe -m launcher` imports the sibling `launcher` package, and a `._pth` forces isolated mode so cwd/`PYTHONPATH` are unavailable as alternatives. Three compensating controls verified present (see the register row): stdlib-zip-first ordering, `import site` omitted, stdlib-only imports. The residual — a module planted at `<install_root>\<name>.py` could be imported by the launcher — requires write access to the per-user install root, at which point the attacker can simply overwrite `launcher\swap.py` and gain the same capability with less effort. No privilege boundary is crossed: the install is per-user (`PrivilegesRequired=lowest`), so this is same-user-to-same-user. **Revisit trigger:** any move to a machine-wide (`{commonpf}`/admin) install, or the launcher gaining a non-stdlib import. | gsd-security-auditor | 2026-09-03 |
| AR-31-SC-PIN | T-31-SC | **The embeddable SHA-256 pin is a download-integrity check, not a publisher attestation.** `EMBEDDABLE_SHA256["3.13.1"]` was established by MD5-matching the download against python.org's published `d5c8030976b5eaf55ed6b321c073dda7` and then SHA-256-ing that same file (`build_release.py:71-80`). MD5 is not collision-resistant and the SHA-256 is self-computed. Accepted because: (1) the *declared* mitigation — "verifies the embeddable SHA-256 against an `EMBEDDABLE_SHA256` pin" — is fully implemented, including the fail-closed refusal of unpinned versions; (2) the honest provenance is recorded **in the code**, next to the value, with the upgrade path named (verify the release's GPG/sigstore signature at the next bump); (3) the pin still defeats the realistic threat here — a tampered or truncated download, or a silent version drift — since any deviation from the exact bytes that were audited once aborts the build; (4) ASVS L1 has no third-party-artifact attestation requirement. **Revisit trigger:** the next Python version bump (do it via GPG/sigstore), or any move to an untrusted build box. | gsd-security-auditor | 2026-09-03 |
| AR-31-SC-WHEELS | T-31-SC | **Vendored wheels are version-locked but NOT hash-verified at install time.** `vendor_wheels` runs `uv export --frozen --no-dev --no-hashes` (`build_release.py:142`) and feeds the result to `pip install --target … --no-deps -r` (`:146-159`). `uv.lock` contains 547 `hash =` entries; `--no-hashes` strips every one of them, so pip downloads from PyPI with TLS as the only integrity control and no `--require-hashes` enforcement. Accepted, **not** treated as a missing mitigation, because: (1) the declared T-31-SC control for this component is "wheels are already-locked `uv.lock` deps with no new PyPI runtime package" — version locking IS present (`--frozen` reads `uv.lock` verbatim) and the zero-new-package half is git-verified; hash pinning was never in the register; (2) `--no-hashes` was an explicit plan-time decision, recorded at `31-04-PLAN.md:99`, not an implementation deviation; (3) ASVS L1 does not require build-time dependency hash pinning; (4) exposure is limited to the build box at build time, and the resulting archive is itself SHA-256-bound and Ed25519-signed (T-31-03) before it reaches any operator. **This is the weakest link in the phase's supply-chain story and should be closed cheaply:** drop `--no-hashes` and add `--require-hashes` to the pip invocation. **Revisit trigger:** the fix above, any CI-hosted (non-local) build of a published release, or the next `pyproject.toml` dependency addition. | gsd-security-auditor | 2026-09-03 |
| AR-31-SC-TOOLING | T-31-SC | **The test scaffold shells out to whatever `minisign` is on PATH.** `tests/test_release_verify.py:109-125` invokes the binary by bare name; in CI that is the Ubuntu-packaged `minisign` (`ci.yml:70`, built from jedisct1 source but distro-repackaged rather than the upstream release binary), and locally it is the developer's own installation (verified on this box: `/c/Users/Admin/scoop/shims/minisign`). Accepted as the plan-01 test-tooling `accept` half of T-31-SC: the binary is used ONLY to prove the sign/verify primitive over a throwaway tmp keypair; it never touches the production secret key (which is offline) or `app/minisign.pub`, and its output gates nothing that ships. Phase 32's runtime verification does **not** depend on it — `app/services/minisign_verify.py` is a pure-Python Ed25519 verifier. **Revisit trigger:** any use of the shelled-out binary on a path that produces or validates a shipped artifact. | gsd-security-auditor | 2026-09-03 |
