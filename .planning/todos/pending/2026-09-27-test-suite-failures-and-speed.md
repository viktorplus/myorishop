# Починить падающие тесты sync_ui и ускорить полный прогон

**Area:** tests
**Created:** 2026-09-27
**Status:** pending

## Problem

1. Полный `uv run pytest -q` локально стабильно даёт 4 падения в
   `tests/test_sync_ui.py`:
   - `test_sync_run_returns_oob_partial`
   - `test_offline_run_returns_200_ru`
   - `test_not_configured_run_is_a_noop`
   - `test_lock_hit_returns_locked_partial`

   Известная версия причины: `sync_client._run_lock` держит поток автосинхронизации,
   который стартует в lifespan приложения, поэтому тесты видят «занято» вместо
   ожидаемого ответа. Падения тянутся с коммита ≤ `49a53d2`. Из-за них каждый
   прогон приходится разбирать вручную, а `-x` останавливается на первом же.

2. Полный прогон идёт ~7–7,5 минут (1808 passed, 2026-09-27).
   Гипотезы (needs verification):
   - фикстура `engine` (`tests/conftest.py:26`) на КАЖДЫЙ тест создаёт новый
     файл SQLite и выполняет `Base.metadata.create_all` + триггеры;
   - часть тестов гоняет полную цепочку Alembic 0001→head (`alembic_engine`,
     `run_alembic`);
   - нет параллельного запуска (pytest-xdist не подключён).

## Solution

- Отключать автосинхронизацию в lifespan под тестами (или отпускать
  `_run_lock` в фикстуре), чтобы 4 теста sync_ui проходили детерминированно.
- Замерить `uv run pytest -q --durations=30` и начинать с самых медленных.
  Кандидаты: одна схема на сессию с откатом транзакции на тест, шаблонный
  файл БД, копируемый вместо `create_all`, pytest-xdist (новая
  dev-зависимость, её нужно согласовать).
- Проверка: полный прогон зелёный без `--deselect`, и время заметно меньше 7 минут.
