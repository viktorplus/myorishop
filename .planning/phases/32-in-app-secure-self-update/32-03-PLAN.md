<objective>
Wave 2 of Phase 32: build the two read-side security primitives — the pure-Python
minisign/Ed25519 verifier (the one genuinely new primitive) and the update
`check_for_update` half that detects a newer signed release, offline-safe and
server-no-op.

The verifier delegates the actual Ed25519 math to `cryptography` (never hand-rolled,
CLAUDE.md safety) and parses only the tiny, documented minisign envelope. It is
algorithm-agnostic (`Ed` raw vs `ED` BLAKE2b-512-prehashed) so a signature from
either minisign mode verifies (32-RESEARCH Pitfall 1).

`check_for_update` composes four shipped idioms: the dialect no-op gate (UPD-06,
copied verbatim from `backup.startup_backup`), the offline-safe httpx posture
(UPD-01, from `sync_client`), the integer anti-downgrade compare (UPD-05), and
the verify-before-trust rule — it reads the offered version from the
SIGNATURE-VERIFIED manifest, never from the mutable git tag (UPD-02/05).

This plan defines the `UpdateStatus` interface that Waves 3 (apply) and 4 (UI)
consume, so those waves build against a fixed contract (interface-first).

Purpose: concentrate the trust logic (verify + compare) in tested pure services
before wiring any route or launcher.
Output: `app/services/minisign_verify.py` (new) + the check half of
`app/services/update.py` (new).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub API/CDN -> app | The `/releases/latest` JSON, `tag_name`, `body`, and asset URLs are all UNTRUSTED input crossing into the client |
| downloaded manifest -> trusted version | The version used for the anti-downgrade decision is only trusted AFTER the Ed25519 signature verifies |
| app engine dialect -> update path | The whole path exists only for the SQLite client; the PostgreSQL server is a hard no-op |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-01 | Tampering / Elevation | minisign_verify + check_for_update | mitigate | verify_minisign (Ed25519 over the manifest against vendored `app/minisign.pub`) must return True before the version is read; a forged manifest -> state "error", nothing offered (ASVS V6/V10) |
| T-32-02 | Tampering | is_strictly_newer | mitigate | Integer `"1.<N>"` compare from the signed manifest; refuse anything not strictly newer, incl. the 9->10 boundary (ASVS V10) |
| T-32-03 | Tampering / Information Disclosure | GitHub download over network | mitigate | HTTPS to GitHub + signature/checksum make transport tampering detectable; asset host allowlist `{github.com, objects.githubusercontent.com}` (ASVS V5) |
| T-32-04 | Tampering | mutable git-tag substitution | mitigate | Trust the `version=` inside the signature-verified manifest; `tag_name` only locates the release, never authorizes the version (ASVS V10) |
| T-32-09 | Denial of Service | PostgreSQL server self-update | mitigate | Dialect gate returns "noop" BEFORE any fetch, mirroring backup.startup_backup (ASVS V1) |
| T-32-10 | Denial of Service | offline/rate-limited fetch | mitigate | `httpx.HTTPError` -> state "offline", whole body broad-guarded; never raises, never blocks the caller (ASVS V1) |
| T-32-SC | Tampering | pip installs | accept | No package install in this plan; `cryptography` vetted in Plan 02 |
</threat_model>
