<objective>
Wave 3 of Phase 32: build the WRITE half — the verify-before-unpack apply
pipeline (the highest-severity control) plus the stronger post-update health
check that confirms the swap actually took.

`update.apply` orchestrates the hard gate exactly in the RESEARCH order: download
the (large) archive + reuse the already-fetched manifest/sig -> (a) Ed25519 verify
the manifest against `app/minisign.pub`, (b) SHA-256(archive) == manifest.sha256,
(c) re-confirm the trusted version is still strictly newer -> ANY failure aborts
with NOTHING staged -> zip-slip-guarded `extractall` into `install_root/staged`
-> `backup.create_backup()` (the shipped VACUUM INTO, UPD-04 anchor) into the
sibling `data/backups` -> write `data/pending.json` with the exact 3-key schema
the shipped launcher's `parse_pending` demands. The app does NOT self-kill — the
already-running launcher (watching every 2s) stops/swaps/migrates/restarts and, on
any failure, performs the shipped matched-pair rollback (code + DB together).

To make UPD-04's post-update health check a real guarantee (32-RESEARCH OQ-3 +
Pitfall 6), add a public `GET /health` returning the installed `APP_VERSION` and
strengthen the launcher's `health_ok` to require the served version equals
`pending.expected_version`. This closes the "stale/wrong staged dir applied"
defense-in-depth gap in the same move.

Purpose: the security gate and the rollback guarantee live here; everything is
either reused shipped code or a tightly-scoped new orchestration.
Output: the apply half of `app/services/update.py`, `app/routes/health.py` (new,
wired + made public), and the launcher health-check strengthening.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| downloaded archive -> filesystem | The archive is attacker-influenceable bytes; it must be signature+checksum verified BEFORE any extract |
| zip members -> staged directory | Archive member paths are untrusted; each must be confined under install_root/staged (zip-slip) |
| app -> launcher (pending.json) | The marker crosses the process boundary; the shipped parse_pending confines its paths (reused, not re-solved) |
| launcher -> running app (/health) | The post-swap health probe must confirm the NEW version actually serves, not just that something answered |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-01 | Tampering / Elevation | apply verify gate | mitigate | Ed25519 verify AND SHA-256 both pass before any `extractall`; failure -> "verification_failed", nothing staged (ASVS V6/V10) |
| T-32-02 | Tampering | apply anti-downgrade re-check | mitigate | is_strictly_newer re-asserted against the verified-manifest version at apply time before staging (ASVS V10) |
| T-32-03 | Tampering / Information Disclosure | archive download | mitigate | HTTPS + asset host allowlist re-asserted; SHA-256 over the signed manifest detects any transport tampering (ASVS V5) |
| T-32-05 | Tampering | zip-slip on unpack | mitigate | `_extract_guarded` rejects any member resolving outside install_root/staged before extractall (ASVS V12) |
| T-32-06 | Tampering | pending.json path traversal | mitigate | Marker written with exactly 3 keys + relative paths; the shipped `parse_pending` confines them (ASVS V12) — reused, not re-implemented |
| T-32-08 | Denial of Service | half-applied update / data loss | mitigate | Pre-update VACUUM INTO backup + the shipped matched-pair rollback; the /health version-match makes a bad swap trigger rollback (ASVS V10) |
| T-32-09 | Denial of Service | PostgreSQL server | mitigate | apply dialect-gates to "noop" before any download (ASVS V1) |
| T-32-SC | Tampering | pip installs | accept | No package install in this plan; `cryptography` vetted in Plan 02 |
</threat_model>
