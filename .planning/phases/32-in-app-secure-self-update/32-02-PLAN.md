<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PyPI -> app site-packages | An unvetted install could ship malicious code that later runs as the update verifier — the highest-leverage supply-chain surface |
| offline signer -> vendored public key | `app/minisign.pub` is the sole trust anchor; a wrong/attacker key would make forged updates verify |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-SC | Tampering | `uv add cryptography` (pip/PyPI install) | mitigate | Blocking-human checkpoint verifies the package on pypi.org (PyCA provenance, correct wheel) BEFORE install; never auto-approvable |
| T-32-07 | Information Disclosure | Ed25519 signing key material | mitigate | Only the PUBLIC key is vendored (`app/minisign.pub`); the secret key stays offline, `.gitignore` blocks `*.key` (inherited T-31-02) — the human checkpoint re-confirms this posture |
| T-32-01 | Tampering / Elevation | trust anchor for release verification | mitigate | The vendored `RW…` public key is the anchor the Wave 2/3 gate verifies every release manifest against; a wrong key is caught here by matching it to the offline signer |
</threat_model>
