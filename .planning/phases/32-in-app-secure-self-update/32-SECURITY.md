# Phase 32 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.
> Phase 32 gives the shipped Windows client an **in-app self-update path**: it asks
> GitHub for the latest release, authenticates the release manifest with Ed25519
> against a vendored public key, refuses anything not strictly newer, verifies the
> archive's SHA-256 against that *signed* manifest, unpacks it zip-slip-guarded into
> `staged\`, takes a `VACUUM INTO` backup, and hands a `pending.json` marker to the
> Phase-31 launcher. The attack surface is therefore **untrusted network input
> (GitHub JSON, release notes, manifest, archive) → code that later executes as the
> operator**, plus one new public HTTP route (`GET /health`).
>
> Every `mitigate` row below was VERIFIED present in implemented code. Plan text,
> SUMMARY claims and code comments were NOT accepted as evidence — each row cites
> the exact line performing the control plus the test or live UAT step that proves
> it. The auditor independently re-ran
> `uv run pytest tests/test_update.py tests/test_launcher.py -q -rs` on 2026-09-03
> at HEAD `68aa97c` → **35 passed, 1 skipped**. The single skip is
> `test_health_ok_requires_version_match` (WinError 10013 binding `127.0.0.1:8000`,
> the operator's own instance owns that port); its control is instead proven LIVE in
> `32-UAT.md` test 3(b). `test_minisign_pure_python_verify` did **not** self-skip —
> `minisign` is on this box's PATH, so the real-binary → pure-Python Ed25519
> round-trip genuinely ran.

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| GitHub API → app | `https://api.github.com/repos/viktorplus/myorishop/releases/latest` JSON is wholly untrusted: `tag_name`, `body`, asset names and asset URLs | Release metadata |
| GitHub CDN → app | `manifest.txt`, `manifest.txt.minisig` and the multi-MB onedir `*.zip` are attacker-influenceable bytes until verified | Manifest + signature + archive |
| downloaded manifest → trusted version | The version driving the anti-downgrade decision becomes trusted ONLY after the Ed25519 signature verifies against `app/minisign.pub` | `version=`, `sha256=` |
| offline signer → vendored public key | `app/minisign.pub` is the sole trust anchor; a wrong key would make forged updates verify | 42-byte `alg‖key_id‖pubkey` |
| zip members → `staged\` | Archive member paths are untrusted and must be confined before extraction | File paths |
| app → launcher (`data/pending.json`) | The marker crosses a process boundary and is the ONLY input that makes the launcher rename directories and run `alembic` | 3-key JSON, relative paths |
| launcher → running app (`GET /health`) | The post-swap probe must confirm the NEW version actually serves | `{"version", "status"}` |
| GitHub release fields → admin's browser | `body` / versions reach the HTML of the confirm screen | Release notes |
| app engine dialect → whole update path | The path exists only for the SQLite client; the PostgreSQL server is a hard no-op | — |

## Accepted Risks Log

| Risk ID | Threat Ref | Rationale | Accepted By | Date |
|---------|------------|-----------|-------------|------|
| AR-32-NOTES | T-32-01 (residual) | **The «Что нового» release notes are displayed from the UNSIGNED GitHub release `body`.** `verified_manifest_version` returns `(version, release.get("body"))` (`app/services/update.py:170`) and the body renders at `app/templates/partials/update_panel.html:27`. The *version* is signature-bound; the *notes* are not — they are protected against XSS (Jinja autoescape, no `\|safe`) but not against tampering. Anyone who can edit the GitHub release text **without holding the signing key** (a compromised GitHub account or token) can put arbitrary Russian copy on the confirm screen — a social-engineering surface ("нажмите X", "отключите Y"), not code execution: the archive that installs is still Ed25519+SHA-256 bound. Accepted for a single-operator local client at ASVS L1. The declared T-32-01 control (autoescape + version-shape validation) is fully implemented, so this does not reopen the threat. **Note the docstring at `app/routes/settings.py:91` overstates the guarantee** ("echoed AUTOESCAPED via the cached status (T-32-01)") — it should say the notes are unverified. **Revisit trigger:** moving notes into the signed `manifest.txt` (a `notes=` line), any multi-operator distribution, or the first report of a misleading release body. | gsd-security-auditor | 2026-09-03 |
| AR-32-HEALTH | T-32-08 (residual) | **`GET /health` discloses the running app version to any unauthenticated caller.** `app/routes/health.py:19-22` is in `PUBLIC_PATHS` (`app/services/security.py:45`) and is included with no `dependencies=` (`app/main.py:206`). This is required: the launcher probe is anonymous and stdlib-only, and the version match IS the T-32-08 control — a `{"status":"ok"}`-only response would silently disable the matched-pair rollback trigger. On the SQLite client the route is loopback-only. On the internet-facing PostgreSQL server the same route ships and leaks `__version__` to anonymous callers (the launcher never polls the server, so it gains nothing there). Accepted: version disclosure of a private-repo app aids only version-specific attacks that would still need an authenticated path, and ASVS L1 has no requirement here. **Revisit trigger:** the server becoming a broader target, or any move to serve `/health` on a public route with a non-loopback bind — then dialect-gate the route or return the version only to `127.0.0.1`. | gsd-security-auditor | 2026-09-03 |
| AR-32-SC-WHEELS | T-32-SC (inherited AR-31-SC-WHEELS) | **The vendored `cryptography` wheel is version-locked but NOT hash-verified at bundle time.** `build_release.vendor_wheels` runs `uv export --frozen --no-dev --no-hashes` (`build_release.py:142`) and feeds the result to `pip install --target`, stripping the `uv.lock` hash that Phase 32 just added for the Ed25519 provider. This matters slightly more now than in Phase 31: `cryptography` is the library that *implements* the update trust gate, so a substituted wheel would silently defeat T-32-01 rather than merely corrupt an unrelated feature. Accepted rather than reopened because (1) the declared T-32-SC control — a human-verified, version-locked install — IS implemented; hash enforcement was never in the register; (2) it was a documented Phase-31 plan-time decision (`31-04-PLAN.md:99`), not a Phase-32 deviation; (3) exposure is the build box at build time, and the resulting archive is itself SHA-256-bound and Ed25519-signed before it reaches any operator; (4) ASVS L1 does not require build-time dependency hash pinning. **This remains the cheapest open hardening in the whole distribution story:** drop `--no-hashes` and add `--require-hashes`. **Revisit trigger:** any CI-hosted build of a published release, or the next dependency addition. | gsd-security-auditor | 2026-09-03 |

## Residual / Advisory Notes (non-blocking)

These do NOT reopen any threat — every declared mitigation is present in code.

| Ref | Note | Disposition |
|-----|------|-------------|
| SEC-A1 | **The trust gate is duplicated, and only one copy is exercised end-to-end (WR-03).** Asset extraction, the host-allowlist loop, the manifest+sig download and the `verify_minisign` call exist twice — `verified_manifest_version` (`app/services/update.py:138-172`) and `verify_release` (`:283-330`). Both currently implement the same ordering and the same allowlist, verified line by line during this audit, so no divergence exists **today**. The hazard is future edits: relaxing one copy would silently weaken either the offer path or the install path. Recommend the single `_download_verified_manifest` helper the review proposes. | advisory |
| SEC-A2 | **Asset URLs are host-checked but not scheme-checked, and redirects are followed unvalidated.** `urlparse(url).hostname not in _ALLOWED_ASSET_HOSTS` (`app/services/update.py:158`, `:306`) accepts `http://github.com/...` as readily as `https://`, and `_download` sets `follow_redirects=True` (`:110`) without re-applying the allowlist to the redirect target. Impact is bounded to transport confidentiality: every byte that matters is afterwards Ed25519- or SHA-256-verified against the signed manifest, so a downgraded or redirected fetch cannot install anything. Two-line fix: assert `urlparse(url).scheme == "https"` in the same loop, and re-check `resp.url.host` after the redirect. | advisory |
| SEC-A3 | **The host allowlist has ZERO automated coverage, and `32-VERIFICATION.md` says otherwise.** A grep of `tests/` for `_ALLOWED_ASSET_HOSTS` / allowlist returns no match; no test feeds a release whose asset URL points off-host. Meanwhile `32-VERIFICATION.md:136-139` states the live gap is "covered only by unit tests" — those unit tests do not exist. Compounding it, `32-UAT.md:31-32` records that `_ALLOWED_ASSET_HOSTS` was **widened at runtime to include `127.0.0.1`** for the live run, so the control was not exercised there either. The control itself is present and correct in code (both call sites), which is why T-32-03 stays closed — but it is the one T-32-03 sub-control with no execution evidence at all. Cheapest close: one test asserting `verify_release` returns None for an `evil.example.com` asset URL. | advisory |
| SEC-A4 | **The zip-slip guard has no adversarial test.** `_extract_guarded` (`app/services/update.py:333-348`) is correct by inspection — the full-namelist pre-scan genuinely precedes `extractall`, and both `../` and drive-absolute members resolve outside `root` — but nothing in `tests/` constructs an archive containing such a member. `test_verify_gate` only proves the weaker "nothing is staged when the *signature* gate fails". A ~10-line test writing `zf.writestr("../evil.txt", ...)` and asserting `pytest.raises(ValueError)` plus the absence of the escaped file would convert this from inspected to proven. | advisory |
| SEC-A5 | **`apply()` can fail AFTER extraction and report a rollback that never happened (WR-02).** `backup_path.relative_to(root)` (`app/services/update.py:423`) raises `ValueError` when `settings.backup_dir` is not under the derived install root — reachable via a `BACKUP_DIR` env override. That happens after `_extract_guarded` has already written `staged\`, so `settings_update_apply`'s `except Exception` (`app/routes/settings.py:101-104`) shows the reassuring «Восстановлена предыдущая версия, ваши данные в безопасности» while in fact nothing was installed, nothing was rolled back, and a fully-extracted `staged\` is left on disk until the next apply cleans it. Not a T-32-08 failure (no data is lost and no half-swap occurs — the launcher never sees a marker), but the operator is told something untrue. Fix: guard the `relative_to` conversion, or compute it before extracting. | advisory |
| SEC-A6 | **`assert` is used for a security-relevant format check (IN-01).** `assert raw[:2] == b"Ed"` (`app/services/minisign_verify.py:36`) validates the pubkey algorithm marker and would vanish under `python -O`. Impact is nil in practice: the input is the vendored trust anchor, and `verify_minisign` is fail-closed, so a malformed key still fails the downstream Ed25519 verify. Replace with an explicit `raise ValueError`. Related fail-closed fragilities, both harmless: `sha256_matches` compares hex case-sensitively without normalisation (`:74-75`, IN-02), and `_archive_url` picks the first `*.zip` by dict order rather than reading the manifest's `archive=` field (`update.py:275-280`, IN-03) — a wrong pick fails the SHA-256 gate rather than installing wrong code. | advisory |
| SEC-A7 | **`pyproject.toml` uses `>=`, not `==`.** `cryptography>=49.0.0` (`pyproject.toml:8`) means a fresh `uv lock` could float the Ed25519 provider to a newer major without a second human checkpoint; today the pin lives only in `uv.lock:201` (49.0.0), which `--frozen` does honour.
