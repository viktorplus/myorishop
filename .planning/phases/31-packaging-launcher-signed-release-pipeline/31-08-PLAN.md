<decisions_verified>
These four facts were verified empirically on this machine on 2026-09-03 against the real
`dist/app` embeddable runtime (Python 3.13.1). Do NOT re-litigate them; build on them.

1. **A `._pth` file forces isolated mode.** `dist/app/python.exe -c "import sys; print(sys.path,
   sys.flags.safe_path, sys.flags.isolated)"` prints `isolated 1`, `safe_path True`, and a `sys.path`
   containing EXACTLY the `._pth` lines resolved against the executable's directory. The current
   working directory and `PYTHONPATH` are NOT on it.
2. **Therefore a WorkingDir- or PYTHONPATH-based `-m launcher` cannot work.** With the stock `._pth`,
   `python.exe -c "import launcher"` from the repo root fails with `ModuleNotFoundError: No module
   named 'launcher'`. A `.bat`/`.vbs` wrapper that sets `PYTHONPATH` cannot fix it — the variable is
   ignored in isolated mode.
3. **A `..` line in the runtime's own `._pth` is what makes it work.** With `._pth` =
   `python313.zip` / `.` / `..`, running `<root>\launcher\python.exe -m launcher` executed
   `<root>\launcher\__main__.py` from an unrelated cwd (`C:\Windows`), because `..` resolves to the
   install root and the launcher package is `<root>\launcher\`. Verified for `pythonw.exe` too.
4. **The launcher must not run on `app\python.exe`.** Renaming a directory whose `python.exe` is
   running SUCCEEDS on Windows (so `app→app.prev` would not fail), but `shutil.rmtree(app.prev,
   ignore_errors=True)` on that same directory silently FAILS and leaves it behind — measured. Running
   the launcher out of `app\` would therefore leak a full copy of the bundle on every successful
   update and violate PKG-04's "launcher lives outside the swappable code directory".

**Console choice (locked): `python.exe`, not `pythonw.exe`.** Tradeoff: a console window stays visible
while the app runs. That is deliberate — it mirrors today's `run.bat` experience, it is the only place
the operator sees the «Migration failed - server not started» abort from Plan 31-06, it gives a
visible "close this window to stop the app" affordance, and with `pythonw.exe` the console-mode uvicorn
child would pop its own window anyway unless `CREATE_NO_WINDOW` were added to `AppProcess.start`.

**Size:** a second embeddable runtime adds roughly 15 MB on disk (~10 MB in the release zip). Accepted
— it is the price of the launcher being outside the swap target.
</decisions_verified>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| installer → %LOCALAPPDATA%\MyOriShop | Per-user, non-elevated install root that any user-level process can write to |
| Start-Menu shortcut → its target file | The operator clicks this; whatever sits at the target path runs with the operator's rights |
| python.org embeddable zip → dist\launcher | A second extraction of the same downloaded runtime artifact |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-08 | Elevation / Tampering | Start-Menu shortcut target | mitigate | NEW. A shortcut pointing at a NON-EXISTENT path inside a user-writable install root is a plant-and-hijack surface: any process able to write `%LOCALAPPDATA%\MyOriShop\launcher\launcher.exe` would own the operator's click. The target now names a file the installer actually ships, and `test_iss_referenced_paths_exist_in_dist` fails the build if any referenced path is missing |
| T-31-SC | Tampering (supply chain) | second embeddable runtime | mitigate | The launcher runtime is extracted from the SAME `fetch_embeddable` artifact whose SHA-256 was verified against the `EMBEDDABLE_SHA256` pin — one verified download, two extractions; no second network fetch is added |
| T-31-06 | DoS (data integrity) | launcher runtime location | mitigate | The launcher runs from `launcher\`, outside the swap target, so `shutil.rmtree(app.prev)` actually succeeds after a good update (a running image cannot be deleted — measured) and no stale copy of the previous bundle survives |
| T-31-01 | Spoofing (user-trust) | unsigned installer / SmartScreen | accept | Unchanged: documented one-time RU «Выполнить в любом случае» step; the shortcut now targets a stock python.org `python.exe`, which does not change the unsigned-installer posture |
</threat_model>
