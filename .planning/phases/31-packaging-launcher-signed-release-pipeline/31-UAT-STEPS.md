# Phase 31 — Пошаговый план UAT (ручная проверка)

Все 4 теста требуют действий на реальных машинах (чистая Windows-ВМ, офлайн-машина,
GitHub Actions), поэтому их нельзя проверить из терминала. Ниже — точный порядок
действий. Текущая версия приложения: **1.14** (`app/__init__.py`), тег `v1.14`
**уже занят** → для реального прогона пайплайна берём следующую версию **1.15**.

## Рекомендуемый порядок (из-за зависимостей)

Артефакты создаёт пайплайн, поэтому логичный порядок: **Тест 3 → Тест 4 → Тест 1 → Тест 2**.

- Тест 3 (ключи) даёт публичный ключ, который попадает в сборку.
- Тест 4 (пайплайн) собирает `MyOriShop-Setup-1.15.exe` — его же ставим в Тесте 1.
- Тест 1 даёт установленный экземпляр, на котором гоняем свап в Тесте 2.

## Тест 3 — Офлайн-генерация ключей minisign + вендоринг публичного ключа (PKG-05)

Делается **один раз**. Нужна установленная утилита `minisign`.

1. На **офлайн-машине** (не CI, не дев-бокс) выполнить:
   ```bash
   minisign -G
   ```
   Появятся два файла: `minisign.pub` (публичный, безопасно) и `minisign.key` (СЕКРЕТНЫЙ).
2. **Секретный ключ** `minisign.key` убрать в офлайн-хранилище (шифрованная флешка /
   менеджер паролей). Никогда не коммитить, никогда не класть в GitHub Actions secrets.
3. Скопировать **только** публичный ключ в репозиторий и закоммитить:
   ```bash
   cp minisign.pub app/minisign.pub
   git add app/minisign.pub
   git commit -m "chore(31-05): vendor operator minisign public key"
   ```
4. **Проверить содержимое:** строка ключа в `app/minisign.pub` начинается с `RW`.
5. **Проверить, что секрет не попал в git:** `git status` не показывает `*.key`
   (файл заблокирован `.gitignore`).
6. **Проверить тест:** ранее пропускавшийся тест теперь зелёный:
   ```bash
   uv run pytest tests/test_release_verify.py::test_vendored_pubkey_present_and_bundled -q
   ```
   Ожидание: `1 passed` (а не `skipped`).

**Успех, если:** есть `app/minisign.pub` (начинается с `RW`), секрет не в git, тест зелёный.

## Тест 4 — Реальный прогон пайплайна подписанного релиза (PKG-05)

### Стадия A — сборка и черновик (GitHub Actions, без секретов)

1. **Запинить SHA-256 встраиваемого Python.** Открыть https://www.python.org/downloads/release/
   (напр. 3.13.1), найти SHA-256 для `python-3.13.1-embed-amd64.zip` и вписать в
   `build_release.py` → словарь `EMBEDDABLE_SHA256`:
   ```python
   EMBEDDABLE_SHA256 = {
       "3.13.1": "<проверенный sha256 hex с python.org>",
   }
   ```
   (Сейчас словарь пустой — без пина `fetch_embeddable` откажется качать рантайм, T-31-SC.)
2. **Поднять версию** в `app/__init__.py`: `__version__ = "1.15"`. Закоммитить
   (вместе с пином SHA).
3. **Толкнуть тег**, совпадающий с версией:
   ```bash
   git tag v1.15
   git push origin v1.15
   ```
   (Либо без тега: Actions → **release** → **Run workflow** → ввести `version=v1.15` —
   это dry-run.)
4. **Проследить пайплайн** `.github/workflows/release.yml` на Windows-раннере. Он должен:
   собрать onedir (`dist\app` + `dist\launcher` + `MyOriShop-1.15.zip`), скомпилировать
   `MyOriShop-Setup-1.15.exe` (Inno Setup), записать `SHA256SUMS` + `manifest.txt`,
   создать **ЧЕРНОВИК** релиза с этими 4 файлами. Секреты не используются.

### Стадия B — подпись офлайн (человек)

5. Скачать `manifest.txt` из черновика релиза на офлайн-машину.
6. Подписать секретным ключом:
   ```bash
   minisign -S -m manifest.txt -t "MyOriShop 1.15"
   ```
   Появится `manifest.txt.minisig`.
7. (Санити-чек) Проверить свою же подпись:
   ```bash
   minisign -Vm manifest.txt -p minisign.pub
   ```

### Стадия C — публикация (человек)

8. Приложить `manifest.txt.minisig` к черновику релиза.
9. Нажать **Publish release**.

**Успех, если:** пайплайн собрал 4 артефакта в черновике, подпись `manifest.txt.minisig`
проверяется публичным ключом, релиз опубликован; секрет ни разу не попал в лог CI.

## Тест 1 — Установка и запуск на чистой Windows (PKG-01, PKG-02)

Нужен `MyOriShop-Setup-1.15.exe` из Теста 4 (или локальной сборки с запиненным SHA).

1. Подготовить **чистую Windows-ВМ БЕЗ** Python / uv / git. Сделать снапшот
   (чтобы откатить после теста).
2. Скопировать `MyOriShop-Setup-1.15.exe` на ВМ и запустить.
3. SmartScreen покажет «Windows защитила ваш компьютер». Нажать **«Подробнее»** →
   **«Выполнить в любом случае»**.
4. Установщик ставит per-user в `%LOCALAPPDATA%\MyOriShop` **без запроса UAC/админа**.
5. Запустить из меню «Пуск» ярлык **MyOriShop**.
6. Через ~2 секунды откроется браузер на `http://127.0.0.1:8000` — должна появиться
   **страница входа**, работающая на **собственном** встроенном Python дистрибутива
   (на ВМ системного Python нет — это и есть проверка автономности).
7. **Проверить установку:**
   - `%LOCALAPPDATA%\MyOriShop\` содержит `app\`, `launcher\`, а `data\` создалась при
     первом запуске (в ней `myorishop.db`).
   - «Параметры → Приложения» показывают **MyOriShop** с рабочим деинсталлятором
     (зарегистрирован per-user).

**Успех, если:** чистая ВМ, SmartScreen пройден один раз, приложение стартовало на своём
рантайме, открылась страница входа, деинсталлятор зарегистрирован.

## Тест 2 — Живой свап + откат парой (PKG-04)

Выполняется на **установленном** экземпляре. Корень установки
`R = %LOCALAPPDATA%\MyOriShop`; лаунчер (`R\launcher\python.exe -m launcher`) должен быть
**запущен** — он раз в 2 секунды смотрит `R\data\pending.json`.
Схема маркера строгая: ровно ключи `staged_dir`, `expected_version`, `db_backup_path`;
пути **относительные** к `R`, без `..`, не абсолютные.

### Часть A — успешный свап

1. Убедиться, что приложение запускалось хотя бы раз → есть `R\data\myorishop.db`.
2. Подготовить «новую версию»: скопировать `R\app` в `R\staged` (это будущий `app`).
3. Сделать резервную копию БД под корнем установки, напр. `R\data\db-backup.db`
   (копия `R\data\myorishop.db`).
4. Создать `R\data\pending.json` с содержимым (пути относительны `R`):
   ```json
   {
     "staged_dir": "staged",
     "expected_version": "1.15",
     "db_backup_path": "data\\db-backup.db"
   }
   ```
5. В течение ~2 сек запущенный лаунчер должен: остановить приложение →
   переименовать `app`→`app.prev` → `staged`→`app` → выполнить `alembic upgrade head` →
   перезапустить → пройти health-check → удалить `app.prev`. Маркер `pending.json` удаляется.
6. **Проверить:** `R\app` — это содержимое staged; `R\app.prev` **исчез**;
   `pending.json` **исчез**; приложение снова отвечает на `http://127.0.0.1:8000`.

### Часть B — откат матч-парой (код + БД вместе)

7. Снова подготовить `R\staged` (копия `app`), но внести **падающую миграцию**: положить
   в `R\staged\alembic\versions\` ревизию, которая гарантированно падает
   (напр. `def upgrade(): raise Exception("boom")` с корректным down_revision на текущую head).
8. Снова сделать `R\data\db-backup.db` и записать `R\data\pending.json` (как в шаге 4).
9. Лаунчер запускает свап; `alembic upgrade head` падает → срабатывает откат:
   `app`→`app.failed`, `app.prev`→`app` (старый код возвращён), БД восстановлена из
   `db-backup.db` (с удалением `-wal`/`-shm`), приложение перезапущено на старом коде.
10. **Проверить:** `R\app` — исходная (старая) версия; `R\app.failed` содержит
    сломанный staged; `R\data\myorishop.db` восстановлена из бэкапа
    (файлов `myorishop.db-wal` / `-shm` нет); приложение отвечает на `:8000`.

**Успех, если:** обе части прошли — чистый свап удаляет `app.prev`, а падение миграции
откатывает **и код, и БД** одной парой.
