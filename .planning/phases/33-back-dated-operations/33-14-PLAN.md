<locked_planner_decisions>
### 1. The mobile «задним числом» filter IS IN SCOPE

`33-UI-SPEC.md` CF-UI-3 flagged that D-20 specifies the fourth select for desktop only while DATE-06
names no surface, and recommended including mobile without folding it in silently. Resolved from the
locked decisions: **D-21 says «Mobile MIRRORS desktop, it does not diverge»**, and the card layout has
no colspan, so the argument that justified divergence elsewhere (the CR-01 pagination scar) does not
apply. A marker the operator can see but cannot filter on the surface they use in the warehouse is
half a feature. It is planned, not deferred.

### 2. The MARKER and the FILTER use two different comparisons, deliberately

This is the one genuinely open design question in this plan, and it is decided here rather than left
to the executor.

- **The marker (display, Python)** compares `business_date` against the **LOCAL calendar day of
  `created_at`**, resolved with `settings.display_tz`. This is `33-UI-SPEC.md` §6's locked rule, and
  the reason is concrete: the migration's backfill is tz-correct, so for every normal historical row
  `business_date == local_day(created_at)` by construction — while `substr(created_at, 1, 10)` is the
  UTC day and differs for every row entered between 21:00 and 24:00 UTC at `Europe/Moscow` (roughly
  00:00–03:00 local). Using the UTC prefix for the marker would falsely stamp «задним числом» on a
  share of perfectly normal rows and make DATE-07's «existing operations keep reporting exactly as
  they do today» visibly false in the UI.

- **The filter (SQL)** compares `business_date` against `func.substr(created_at, 1, 10)`, because
  that is the ONLY form expressible in portable ORM. The local day cannot be computed in SQL without
  a dialect-specific datetime function (`datetime(created_at, '+3 hours')` on SQLite,
  `created_at::date` on PostgreSQL), which CLAUDE.md PC-2 forbids; a stored marker column is also
  out (only four columns land this phase, and the ledger is append-only).

**The accepted, documented consequence:** the two agree on every row except one entered in the window
where the local calendar day differs from the UTC calendar day. On those rows `dated=backdated`
over-includes and the marker correctly stays off. This is the smaller of the two errors — a filter
that returns a few unmarked rows is subtler than a marker that visibly contradicts the date printed
beside it. Applying the marker in Python after the SQL page was fetched is NOT an option: the count
would then disagree with the rows and pagination would break, which is exactly the defect plan 33-08
pins with its `len(rows) == total` assertion.

Write this trade-off as a comment at both the filter predicate and the `is_backdated` computation,
and pin it with a test.
</locked_planner_decisions>
