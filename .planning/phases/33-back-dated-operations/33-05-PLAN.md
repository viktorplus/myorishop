Exact names and shapes. `33-PATTERNS.md:245` calls one of them `reverses_operation_id`; that is a
documentation slip. `.planning/ROADMAP.md` LOCKED constraint 2 is authoritative:

| Table | Column | Model type | Migration type | Nullability |
|-------|--------|-----------|----------------|-------------|
| `operations` | `business_date` | `String(10)` | `sa.String(10)` | nullable, **no `default=`, no `server_default=`** |
| `operations` | `reverses_op_id` | `String(36)` + ORM `ForeignKey("operations.id")` | `sa.String(36)`, **bare column, no FK constraint** | nullable |
| `cash_movements` | `business_date` | `String(10)` | `sa.String(10)` | nullable, no defaults |
| `cash_movements` | `reverses_movement_id` | `String(36)` + ORM `ForeignKey("cash_movements.id")` | `sa.String(36)`, bare column | nullable |

**Why no default of any kind** (V1, executed): SQLAlchemy 2.0.51 removes `None`-valued keys from the
emitted INSERT and substitutes the Python `default=` (or omits the column so the DDL `server_default`
fires). A default therefore *destroys* DATE-08's NULL sentinel — the read-time COALESCE would never
see a NULL from an un-upgraded client. And a `server_default` that is a `ClauseElement`
(`sa.text(...)`, `sa.func.*`) flips Alembic's `requires_recreate_in_batch` to True and would destroy
all four triggers on the way UP.

**Why the FK asymmetry** (model has it, migration does not): the shipped `sale_id` / `batch_id` /
`author_id` precedent. The ORM `ForeignKey` gives merge insert-ordering and PostgreSQL portability;
the migration adds a bare native column so a reversal whose target has not yet arrived renders as a
dangling link instead of rolling back an entire push (Phase 34 LOCKED constraint 4).

**Consequence to state, not to prevent:** `merge.KIND_TO_FIELDS` (`app/services/merge.py:80-83`) is
derived from the model mapper, so these four columns enter the sync wire format automatically the
moment they exist. That is precisely why SYNC-10's 409 gate (plan 33-01) had to land first.
</column_contract>
