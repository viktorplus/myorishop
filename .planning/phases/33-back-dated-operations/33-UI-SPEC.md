# Phase 33 — UI Design Contract

> Visual and interaction contract for Phase 33 «Back-Dated Operations». Generated by gsd-ui-researcher from the 25 LOCKED decisions in `33-CONTEXT.md` and the executed findings in `33-RESEARCH.md`. Verified by gsd-ui-checker.

**This phase adds no new visual language.** It adds one field to 14 existing surfaces, one line to 2 existing list renderers, one `<select>` to one existing filter bar, and one column to 2 existing CSV writers. Everything below either cites an existing `file:line` precedent or is explicitly marked as the single new CSS line this phase is allowed.

**Run mode:** `--auto`, non-interactive. Zero questions were asked; every design question was already settled in the advisor-mode discussion recorded in `33-CONTEXT.md`. This document formalises D-10 … D-14, D-16, D-18 … D-21 and D-23 into markup the executor can copy byte-for-byte.

## Component Contract — the date field

### Canonical markup (desktop, `.stacked-form` surfaces 1, 3, 4, 5)

```html
{# DATE-01/D-10: the business date — visible, pre-filled with today, LAST field
   before .form-actions, identical on every ledger-writing surface. max= is safe
   here: hx-post sits on the <form> and the submit is a native button, so the
   browser's own interactive validation fires first and shows its own bubble
   (33-RESEARCH.md, D-13 verdict). An empty value is not an error — it means
   "today", mirroring parse_optional_expiry (app/services/receipts.py:63-64). #}
<div class="field op-date">
  <label for="op_date">Дата операции</label>
  <input type="date" id="op_date" name="op_date"
         value="{{ form.op_date or today_iso() }}" max="{{ today_iso() }}">
  {% if errors.op_date %}<p class="error">{{ errors.op_date }}</p>{% endif %}
</div>
```

Substitute the per-surface `id=` and `value=` expression from the surface inventory. Everything else — element order, class names, the `.error` paragraph — is byte-identical on all 14 surfaces.

The `<div class="field">` + block `<label for>` + `<input>` + `{% if errors.X %}<p class="error">` shape is the app's uniform desktop idiom, shipped at `partials/receipt_form.html:32-44`, `pages/batch_form.html:40-42`, `partials/withdraw_form.html:21-26`. The `<input type="date">` shape is shipped 11 times (`partials/period_filter.html:31,35`; `pages/batch_form.html:41`; `partials/active_catalog_form.html:14`; `partials/receipt_batch_chooser.html:57`; `partials/transfer_batch_wrap.html:52`; `mobile_pages/batch_edit.html:30`; `mobile_pages/history.html:45,52`; `mobile_partials/receipts_step_details.html:36`; `mobile_partials/transfers_step_dest.html:61`).

### Mobile shell placement (surfaces 9–11) — how it must look

```html
<form id="receipt-form" hx-target="#wizard-step" hx-swap="innerHTML">
  {# DATE-01/D-11: wizard-wide chrome, NOT a step question. It sits ABOVE the
     «Шаг N из M» indicator, which is the first line every step partial renders
     — so the rule for the operator is: everything below the step indicator
     belongs to the current step, everything above it belongs to the whole
     wizard. htmx never swaps this node, so the typed value survives every step
     swap AND a 422 re-render with zero hidden-field threading. #}
  <div class="field op-date">
    <label for="op_date">Дата операции</label>
    <input type="date" id="op_date" name="op_date"
           value="{{ today_iso() }}" max="{{ today_iso() }}">
  </div>
  <div id="wizard-step">
    …
  </div>
</form>
```

**Position is the separation.** No divider, no box, no new colour, no heading. The field renders on its own row directly under the page `<h1>` and directly above `<p class="mobile-step-indicator">Шаг 1 из 4</p>`, which re-establishes step context on the very next line. This is the answer to «visible on every step» — it reads as a setting for the whole entry, because it never moves while the step content below it changes.

**No `<p class="error">` in the shell.** The shell is never re-rendered, so `errors` cannot reach it. The `op_date` error is emitted by the swapped final step instead — see Interaction Contract §5.

### The one new CSS line this phase is allowed

```css
/* DATE-01/D-10 (Phase 33): the business-date field must render on its own row
   on every ledger surface. Four of the 14 forms are bare <form>s and therefore
   inherit `form { display:flex; flex-wrap:wrap }` (style.css:136-142) — the
   3 mobile wizard shells (where the field would otherwise compete for a row
   with #wizard-step) and #sale-form (where it would sit beside the muted
   «Если товара с таким кодом ещё нет…» hint, sale_form.html:85). Inside
   .stacked-form (display:block, style.css:145-148) this rule is inert.
   No new colour, no new spacing token — .field's own 16px margin still applies. */
.field.op-date { flex-basis: 100%; }
```

**Justification for a new rule rather than reuse:** there is no existing full-row modifier in `style.css`. The alternatives are worse — adding `class="stacked-form"` to `#sale-form` would change that form's whole layout (it deliberately uses the flex form to sit the basket table, the running total and the hint in one flow), and wrapping the field in a `<div>` would be a new structural element on 14 surfaces to avoid one declaration. One property, one existing class, one existing selector shape.

**Explicitly NOT added:** `.field.op-date` gets no colour, no border, no background, no font-size, no margin override. If the executor's diff to `style.css` is longer than the comment plus that one declaration, the diff is wrong.

**Exception — surfaces 6 and 14 (возврат, desktop and mobile).** These two forms are also bare `<form>`s, but their existing layout is a deliberate one-row compact form (`return_form.html:33-40`: hidden input + qty field + actions). Here the date field **may** share the row with «Количество к возврату» — that is the correct, denser reading for a two-field confirmation. Therefore surfaces 6 and 14 use `class="field"` **without** `op-date`. This is the only intentional layout divergence in the 14, and it is visible in the surface inventory's `class` usage.

## Interaction Contract

### 1. `today` delivery (D-15)

There is **no `today` Jinja global** — `app/routes/__init__.py:193-231` enumerates all of them (`APP_VERSION`, `WRITEOFF_REASONS`, `OPERATION_TYPE_LABELS`, `CASH_CATEGORIES`, `CASH_BUCKET_LABELS`, `CONTACT_KINDS`, `ROLES`, `CURRENCIES`, `DEFAULT_CURRENCY`, `nav_section`, `batch_identity_label`) and none is a date.

**LOCKED: register a zero-arg callable global `today_iso()`**, not a per-context value.

- Registered beside the existing callable globals at `app/routes/__init__.py:229-231` (`nav_section`, `batch_identity_label` are already registered as callables — this is an established idiom, not a new one).

### 2. Native `<input type="date">` and locale (accessibility + i18n)

The browser renders `<input type="date">` in the **browser's** locale (a Russian-locale browser shows `дд.мм.гггг`; a US-locale browser shows `mm/dd/yyyy`), while the posted value is **always** ISO `yyyy-mm-dd` regardless of locale. This is already documented in this repo at `app/services/receipts.py:52-53` for the expiry field: *«the value must be an ISO yyyy-mm-dd date — which `<input type="date">` always posts, regardless of locale»*.

**Consequences that must be honoured, not compensated for:**

- **Nothing is compensated.** No JS date picker, no locale shim, no format hint next to the field. This is the same contract the app already ships on 11 date inputs and the operator already uses daily.
- The RU display everywhere *else* stays `dd.mm.yyyy` via the `ru_date` filter (`app/core.py:89-99`) and `dd.mm.yyyy HH:MM` via `local_dt` (`app/core.py:102-105`). The input widget is the only place a different rendering can appear, and only if the operator's browser locale is not Russian.
- `OP_DATE_FORMAT_ERROR` naming the ISO shape («ГГГГ-ММ-ДД») is therefore correct and matches the shipped `EXPIRY_ERROR` (`receipts.py:43`). It is a defence-in-depth message: a native date picker cannot produce it. It is reachable only via a browser without `type="date"` support (which degrades to a text input) or a hand-crafted POST — both of which need the ISO shape spelled out.

Every one of the 14 inputs carries `id` + a matching `<label for>`. The two cash forms use prefixed ids (`withdraw-op-date` / `deposit-op-date`) because both render on one page — see the ⚠ note in the surface inventory. The focus ring is the shipped one (`input:focus { outline: 2px solid #2563eb; outline-offset: 1px }`, `style.css:235-241`) — never removed, never replaced.

### 4. `max` and `required`

- **`max="{{ today_iso() }}"` on all 14** — D-13, resolved. `33-RESEARCH.md` read the vendored htmx 2.0.10 source: htmx calls `checkValidity()` (not `reportValidity()`) and `reportValidityOfForms` defaults to `false`, but the feared silent halt needs `hx-post` on a `<form>` *plus* a non-native-submit trigger, which **no** ledger surface has.
  - Surfaces 1–8, 12, 13, 14 (`hx-post` on the `<form>`, native `<button type="submit">`): the browser's interactive validation runs before `submit`, htmx never sees the event, and the operator gets the **native bubble**. Safe.
  - Surfaces 9–11 (the 3 mobile shells, `hx-post` on the `<button>`): htmx `preventDefault()`s the click, so neither native nor htmx validation runs. `max` is **inert** and `OP_DATE_FUTURE_ERROR` from the server is the sole guard — which is the intended fallback anyway.
  - This will be the app's **first live `max` constraint**: the two existing `max` attributes (`partials/return_form.html:35`, `mobile_partials/return_confirm.html:40`) sit on `<input type="text">`, where `max` has no constraint-validation effect at all.
- **No `required`.** An empty value has a defined, safe meaning (today), and `required` would behave asymmetrically across the two htmx idioms — blocking on 11 surfaces, inert on 3. A guard that fires on some screens and not others is worse than no guard when the server already refuses everything invalid.

### 6. История «Когда» — the muted second line (D-18, D-19, D-21)

**Two row-dict keys, added once in `history_view` (`app/services/operations.py:170-183`) and consumed by both surfaces:**

|-----|-------|-------|
| `business_day` | the row's business date as `String(10)` ISO, or `None` | rendered with `\| ru_date` (`app/core.py:89-99`), **never** `\| local_dt` — `iso_to_local("2026-09-01")` would produce a naive datetime and print a bogus time |
| `is_backdated` | `True` **only when** `op.business_date is not None` **and** `op.business_date != ` the **local calendar day of `op.created_at`** resolved with `settings.display_tz` | see the correctness note below |

> **The comparison is against the LOCAL day of `created_at`, not `substr(created_at, 1, 10)`.** The UTC prefix and the local day differ for every row entered between 21:00 and 24:00 UTC at `Europe/Moscow` — roughly the 00:00–03:00 local window. Since the migration's backfill is tz-correct (`.planning/research/SUMMARY.md` § Reconciled Disagreements), a naive UTC-prefix comparison would falsely stamp «задним числом» on a share of perfectly normal historical rows and make DATE-07's «existing operations keep reporting exactly as they do today» visibly false in the UI. This is a display-layer rule; it does **not** change `business_date_expr`, whose SQL fallback stays `func.substr(created_at, 1, 10)` for `NULL` rows.

**Граница между пометкой и фильтром — что оператор реально увидит.**
Пометка «задним числом» и фильтр «Только задним числом» сравнивают даты по-разному, и это осознанный выбор, а не дефект. Пометка сравнивает бизнес-дату с **локальным** днём внесения (по `display_tz`). Фильтр сравнивает её же с днём внесения **по UTC**, потому что только эта форма выражается переносимым ORM-запросом: локальный день в SQL требует диалектных функций (`datetime(created_at, '+3 hours')` в SQLite, `created_at::date` в PostgreSQL), которые запрещены CLAUDE.md PC-2. Совпадают они на всех строках, кроме внесённых в то ночное окно, где локальный календарный день и день по UTC различаются — при `Europe/Moscow` это примерно с 00:00 до 03:00 по местному времени.

Наблюдаемое следствие: выбрав «Только задним числом», оператор может увидеть строку **без** пометки «задним числом». Такая строка внесена в это ночное окно; пометка права — операция внесена в свой же день, — а фильтр захватил лишнее. Обратного не бывает: строка с пометкой всегда попадает в «Только задним числом», ни одна помеченная операция не теряется.

Так выбрано намеренно: фильтр, показавший несколько лишних строк, — меньшая из двух ошибок по сравнению с пометкой, противоречащей дате, напечатанной рядом с ней. Вычислять пометку в Python уже после выборки страницы нельзя: тогда `total` разойдётся со строками и сломается постраничная навигация. Поведение закреплено тестом `test_backdated_filter_and_marker_diverge_only_on_utc_straddle` (план `33-14`). Этот абзац описывает уже принятое поведение и не меняет ни одного решения настоящего документа.

### 7. The fourth История filter (D-20)

A `<select>`, **not** a checkbox — `type="checkbox"` appears exactly once in the whole template tree (`app/templates/pages/settings.html:28`, a settings form, never a list filter); a boolean cannot express «Только в день операции»; and an unchecked checkbox posts nothing, so the `hx-include` idiom would silently drop the state.

Inserted as the **4th `.field`** in `.filter-bar`, after the «Пользователь» field (`history_rows.html:52-63`) and before the closing `</div>` at `:64`:

```html
<div class="field">
  <label for="dated">Задним числом</label>
  <select id="dated" name="dated"
          hx-get="/history" hx-trigger="change"
          hx-include="#history-rows input, #history-rows select"
          hx-target="#history-rows" hx-swap="outerHTML" hx-push-url="true">
    <option value=""{% if not dated %} selected{% endif %}>Все</option>
    <option value="backdated"{% if dated == "backdated" %} selected{% endif %}>Только задним числом</option>
    <option value="same_day"{% if dated == "same_day" %} selected{% endif %}>Только в день операции</option>
  </select>
</div>
```

- **The six HTMX attributes are byte-identical** to the three siblings at `:27-30`, `:39-42`, `:54-57`: `hx-get="/history"`, `hx-trigger="change"`, `hx-include="#history-rows input, #history-rows select"`, `hx-target="#history-rows"`, `hx-swap="outerHTML"`, `hx-push-url="true"`.
- **Option values are Latin keys** (`backdated` / `same_day`), matching the repo's `sort=oldest` and the latin cash-category keys. The default is the empty string, first, selected when `dated` is falsy — the exact idiom of `:31`, `:43`, `:58`.
- **Unknown/tampered values fall back to «Все»** (no filter), the same allow-list discipline as `_SORT_MAP.get(sort, default)` (`app/services/operations.py:28-32`). Never string-interpolated into a query.
- **`history_view` must return `"dated"`** in its result dict alongside `"type_filter"`, `"product_id"`, `"author_id"`, `"sort"` (`app/services/operations.py:190-196`) so the select can re-select itself after a swap.
- **`qs_parts` must carry it** — `app/routes/history.py:129-142` re-serialises the active filter state onto every pagination link (HIST-02). Add `"dated": result["dated"]` to that dict, or paging silently drops the filter.
- **The empty-state condition must learn about it.** `history_rows.html:119` and `:234` read `{% if type_filter or product_id or category or customer or author_id or from_date %}`. Add `or dated`, otherwise filtering to «Только задним числом» with no matches shows «Операций пока нет.» — copy that tells the operator the app is empty when it is not.
- **`_SORT_MAP` / `_DEFAULT_ORDER` are NOT touched** (D-22). This is a filter, never a sort.

> **Manual check at 1024 px (flagged, not this phase's work).** `.filter-bar` (`style.css:188-193`) sets `display:flex; gap:16px` and — unlike `.toolbar` (`:72-77`) — **no `flex-wrap`**. ## Conflicts with locked decisions

Recorded per `--auto` run-mode instructions. **No locked decision is contradicted by this contract.** Two supporting statements are factually wrong and one instruction is unimplementable as literally written; in every case the decision itself survives.

### CF-UI-1 — D-14's «under the date input in all five final steps» is unimplementable on 3 of the 5

`33-CONTEXT.md:170-172` instructs: *«add the per-key branch under the date input in all five final steps»*. The two instructions are jointly unsatisfiable for those three wizards.

**Resolution (does not reopen either decision):** D-11 wins on placement — it is the more specific instruction and the one with the stated mechanical rationale. D-14's *intent* («the date error must not surface as a top-of-screen block detached from the field») is satisfied by emitting the per-key `<p class="error">` as the **first element of the swapped step**, i.e. the DOM node immediately following the shell's date input, and by excluding `op_date` from every loop-all block. See Interaction Contract §5. The literal reading applies unchanged to корректировка and перемещение, where the field really is on the final step.

### CF-UI-2 — D-10's «`<details>` appears nowhere» is false (carried from `33-RESEARCH.md` CF-1)

`33-CONTEXT.md:120-121` rejects a collapsed disclosure partly because *«`<details>` appears nowhere under `app/templates`»*. It appears twice: `app/templates/partials/product_rows.html:81` and `app/templates/partials/user_rows.html:39` (the latter with a comment at `:37-38` calling it *«native `<details>` reveal (no client JS, no extra GET route)»*).

**Impact: none on the decision.** D-10 stands on its two independently sufficient arguments — the operator touches this field often (there is no lower bound on back-dating), and a 422 pointing at a collapsed field is a real usability defect. **Action:** do not repeat the «nowhere in the codebase» claim in any code comment, plan rationale or commit message. A future reader will catch it.

### CF-UI-3 — D-20 is silent on mobile История, and DATE-06 is not

`33-CONTEXT.md:244-253` specifies the «задним числом» filter only for the desktop `.filter-bar`. `.planning/REQUIREMENTS.md:46` (DATE-06) says the marker *«can be filtered on that in История»* without naming a surface, and D-21 (`:255-260`) states the general principle *«Mobile MIRRORS desktop, it does not diverge»* — but says it about the marker rendering, not the filter.

**This is a scope gap, flagged, not silently closed.** The mobile filter is **NOT written into the contract above.** If the planner adds it, the shape is fully determined and costs one `.field`: `app/templates/mobile_pages/history.html` already stacks its filters as `.field` divs inside `#history-filters` (`:15-57`), with the same six-attribute idiom pointing at `hx-get="/m/history"` / `hx-target="#history-cards"` / `hx-include="#history-filters input, #history-filters select"`. **Recommendation:** include it. The marker is mirrored to mobile by D-21, and a marker the operator can see but cannot filter on the surface they use in the warehouse is half a feature.
